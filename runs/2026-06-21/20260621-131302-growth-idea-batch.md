1.  **ID: T01 - n8n JSON修复器**
    *   **目标人群**：使用n8n的开发者、自动化工程师
    *   **痛点**：工作流因JSON格式、转义或结构问题报错，排查耗时。
    *   **最小交付物**：一份可直接使用的Python/Node.js脚本模板（能格式化、验证n8n导出JSON），或一份《常见n8n JSON错误速查表》PDF。
    *   **测试渠道**：n8n GitHub Issues（如`n8n-io/n8n`的bug report）、n8n社区论坛、Reddit r/n8n。
    *   **验证指标**：1. 脚本/GitHub星标数；2. 论坛帖子回复数及“有用”投票；3. 收到JSON文件请求帮忙修复的私信数。
    *   **发布草稿示例**：“看到很多n8n用户被JSON错误卡住。我整理了一个简易脚本，可一键检查常见格式问题。链接：[GitHub Gist]。如果你的工作流也报错，欢迎贴出错误信息（脱敏），我来帮你看看。”

2.  **ID: T02 - AI客服对话模拟训练**
    *   **目标人群**：SaaS公司客服主管、电商卖家
    *   **痛点**：培训新客服成本高，场景覆盖不全，缺乏标准化应答。
    *   **最小交付物**：一个可交互的网页Demo，内置3-5个典型客服对话场景（如退款、技术问题），用AI生成不同难度的客户提问，并展示参考应答。
    *   **测试渠道**：LinkedIn（发布相关观点）、IndieHacker社区、Twitter/X #CustomerSupport 标签。
    *   **验证指标**：1. Demo页面访问量；2. 表单提交（“申请试用完整版”）的数量；3. 相关社群中引发的讨论数。

3.  **ID: T03 - GitHub Issue 自动分类器**
    *   **目标人群**：维护开源项目的技术负责人
    *   **痛点**：Issue量大，手动分类（bug/feature/question）和打标签耗时，影响响应速度。
    *   **最小交付物**：一个开源的GitHub Action脚本，能自动给新Issue添加分类标签。附带一个配置说明文档。
    *   **测试渠道**：在自身GitHub仓库部署、在相关开源项目（如awesome-lists）的Issue中作为“有用工具”分享、Reddit r/github。
    *   **验证指标**：1. GitHub Star/Fork数；2. 在其他仓库被引用的次数；3. 是否收到关于定制化（如接入Slack通知）的咨询。

4.  **ID: T04 - Markdown文档翻译/本地化检查器**
    *   **目标人群**：开源项目维护者、技术文档写作者
    *   **痛点**：技术文档（README等）需要多语言支持，人工翻译成本高，机器翻译生硬。
    *   **最小交付物**：一个基于LLM的命令行工具，输入Markdown文件，输出针对技术文档优化过的翻译建议，或高亮出机器翻译不自然的句子。
    *   **测试渠道**：Twitter/X #OpenSource #DevRel，Hacker News Show HN。
    *   **验证指标**：1. 工具下载/克隆次数；2. 提交的Issues或Feature Requests数量；3. 是否有团队表示愿意资助支持。

5.  **ID: T05 - API速率限制可视化报告**
    *   **目标人群**：调用第三方API（如OpenAI, Twitter）的开发者
    *   **痛点**：不清楚自己的应用对API的调用频率，容易触达限额导致服务中断。
    *   **最小交付物**：一个轻量级的代理层或日志解析脚本，能生成一张可视化报告（如图表），展示过去24小时/周的API调用趋势和剩余配额。
    *   **测试渠道**：Twitter/X #API #DevTools，相关API的Discord/Slack社区。
    *   **验证指标**：1. 脚本被克隆/下载的次数；2. 在社群中被询问“如何部署”的次数；3. 是否收到关于“支持更多API”的定制需求。
